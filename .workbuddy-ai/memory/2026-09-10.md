## Reader + TTS performance review (read-only, no code changed)

Investigated "cập nhật VP và rule nhiều lần → giật lag reader, giật lag khi mở màn hình dịch".

Deliverable: `Docs/Reports/2026-09-10-reader-tts-perf-review.md` (root cause + full reading/TTS review + P0/P1/P2 fix plan).

**Root cause (one sentence):** invalidation is all-or-nothing and global — no incremental path between "one rule/VP entry changed" and "re-translate + re-render the whole chapter".

Key confirmed findings (with line refs at time of review):
- `QuickTranslationRuleStore.writeRecordsLocked` (`:194-235`) serialises + atomically rewrites the whole rule TXT and recompiles **all** rules **synchronously on MainActor** (caller is a SwiftUI action: `ReaderView+RuleTools.saveRuleFromEditor:200`). `moveRule:161` does it **twice**.
- `invalidateTranslationCaches()` (`:396-399`) calls `TranslateUtils.clearCache()` (global) and posts `notifyDictionariesDidUpdate()` with **bookId: nil** — so a **book-scoped** rule edit is a global invalidation (scope bug).
- `TranslateUtils.translationGenerationToken` folds in `QuickTranslationRuleStore.cacheTag` ⇒ any rule change invalidates every book.
- `TranslateUtils.invalidateCache(bookId:)` (`:906-920`) bumps generation but **never empties `translationCache`**, which is an NSCache with **no countLimit/totalCostLimit** (`:5`) and generation-stamped keys ⇒ orphaned entries, RSS growth, memory pressure, chapter eviction.
- `updateCachedTranslatedContent` sets neighbours `translationToken = 0` (`ReaderViewModel+Translation.swift:216-219`) ⇒ `requestChapter` (`ReaderViewModel.swift:474-495`) takes the **refetch** branch instead of the cheap 32 ms memory-commit ⇒ several expensive page turns after one edit.
- Cache sizes: `QuickTranslationRuleEngine` NSCache countLimit **64** (thrashes on any chapter); `TokenizeMemo` 512; both keyed on generation ⇒ permanently cold after each edit.
- Dịch panel: `ReaderDefinitionOverlayView.originalSentenceRowView:158-242` builds **one SwiftUI `Text` per UTF-16 code unit** of the paragraph in a non-lazy `HStack`/`ScrollView` (thousands of views). `openDefinitionPanel` → `updateEditorFromSelection` (`ReaderView+Selection.swift:60`) cold-tokenizes the **whole paragraph** on MainActor (memo key includes generation ⇒ miss right after an edit). Called again by all 4 nới/thu buttons.
- TTS: `TTSManager.swift:968` cancels `nextChapterPrefetcher` on every `bookId == nil` notification ⇒ editing rules while listening is the app's worst case. `TTSBackgroundProcessor` snapshot reuse needs exact `translationToken` match.

## Correction + hard requirement (later same day)
- **CORRECTION to my earlier report:** I had claimed book-scoped rule edits cause a global invalidation (RC-2 / §7 row 4). Global-rule edits being global is **by design**. The only real waste is `moveRule` = copy + delete ⇒ 2 compiles + 2 invalidations. Report has been fixed.
- **User's hard requirement:** after updating dictionary/rules, the **currently read/listened chapter AND all following chapters** must use the new dictionary/rules.
- Verified against that requirement (now §11 of the report):
  - Reader current chapter ✅; cached neighbours ✅ (token=0 → refetch+retranslate); uncached ✅; TOC titles ✅.
  - **TTS currently-playing chapter ❌ — the ONLY gap.** Root cause: `self.chapterContent = processed.normalizedContent` overwrites raw with translated (`:1282`, `:1319`); `TTSPreparedChapter` stores only translated content; `resumeAfterSettings` (`:1643-1658`) re-chunks but never re-translates; the dictionary observer (`:968-984`) only touches prefetch + now-playing. **No raw text is retained ⇒ cannot re-translate.** Fix = new **T8**: retain `playingRawContent`, re-run `processChapter` at `.utility`, swap `paragraphs` at a paragraph boundary (reuse `resumeAfterSettings` index-matching logic `:1677-1690`), keep audio playing.

- Verified "bấm nghe lại ra bản dịch mới" — all paths are correct:
  - `ReaderView.startTTS` (`:1609`) → `getTTSChapterContent` returns `paragraphItems.original` = **raw** (`:1677-1688`), so `processChapter` translates fresh.
  - `getPretranslatedSnapshot` returns nil when `cached.translationToken != currentToken` (`:1654-1658`) ⇒ no stale snapshot reuse.
  - Auto-advance uses a fresh `processChapter` (`:2269`) or a prefetched DTO consumed only on exact key match (key contains token).
  - All `continueStartSpeaking` callers (`:1284`, `:1321`, `:2325`) follow a fresh `processChapter` — no UI path replays stale `paragraphs`.
  - Consequence: first replay after an edit pays a full chapter re-translation (brief delay) — acceptable, it happens on an explicit user tap.
- **Net: the requirement is fully satisfied by current code.** Everything left in the report is pure performance optimisation, not correctness. T4b (defer re-translation until pause) is now explicitly allowed.
- Latest recommended order (§11.5): T1+T2 → T3 → T4a+T5 → T6+T7 → P0-3 last.
- **T4b NOT recommended for this user** (added §11.6 explaining it): "hoãn dịch/dựng chương hiện tại tới khi dừng phát" means the **on-screen Reader text** keeps the OLD translation until you pause. User edits by selecting text on screen ⇒ they are looking at the screen ⇒ T4b produces "vừa sửa mà chữ không đổi". Recommend **T4a** (translate immediately, defer only the rendering of non-visible paragraphs) + T5 (background priority). T4b only suits screen-off / widget-only listening.
- Clarified framing that helped: after an edit there are **two jobs** (dịch = CPU, off-main; dựng = main thread) × **two surfaces** (màn hình Reader / giọng đọc TTS). The user's decision exempted only the TTS surface of the playing chapter; the on-screen surface was still undecided.
