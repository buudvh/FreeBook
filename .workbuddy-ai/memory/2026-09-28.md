## "Push bị sandbox chặn" — chẩn đoán đã xác minh

Người dùng báo `git push` hay bị chặn, kèm screenshot dialog **`CredentialHelperSelector`** (radio `<no helper>` / `manager` / `wincred`).

**Kết luận: sandbox KHÔNG chặn push.** Bằng chứng: `git push --dry-run` chạy tới GitHub thành công, `exit=0`, không dialog, không bị sandbox từ chối.

**Nguyên nhân thật**: WorkBuddy dùng **PortableGit đi kèm**, và file system-config của nó có:

```
C:\Users\hoang\.workbuddy-ai\binaries\PortableGit\versions\1.2.0\etc\gitconfig
[credential]
	helper = helper-selector        # dòng 19-20
```

`helper-selector` là helper **hiện dialog GUI** để hỏi chọn helper ⇒ đó chính là screenshot. Vì đây là system config nên nó áp cho **mọi repo** dùng PortableGit này. Trong phiên agent (non-interactive) dialog GUI không ai trả lời được ⇒ lệnh treo/thất bại ⇒ trông như "bị sandbox chặn".

`~/.gitconfig` cũng có thêm một helper nữa (`git-credential-manager.exe`) nhưng vì `credential.helper` là **key đa trị**, git chạy lần lượt ⇒ `helper-selector` vẫn nổ trước.

**Cách chạy non-interactive đã kiểm chứng** (không cần sửa config gì):

```bash
GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never \
git -c credential.helper= -c credential.helper='!gh auth git-credential' push origin <branch>
```

- `-c credential.helper=` (rỗng) **reset** danh sách helper kế thừa, rồi `-c credential.helper='!gh auth git-credential'` thêm đúng một helper.
- Dùng được vì `gh` **đã đăng nhập sẵn** (`buudvh`, keyring, scope `repo` + `workflow`).
- `GIT_TERMINAL_PROMPT=0` + `GCM_INTERACTIVE=never` để **fail nhanh** thay vì treo chờ dialog.

**Các mức sửa, theo bán kính ảnh hưởng**:

1. Per-command (như trên) — 0 thay đổi config.
2. Per-repo: `git config --local credential.helper ""` + `git config --local --add credential.helper "!gh auth git-credential"` — chỉ repo này, hoàn tác bằng `--unset-all`.
3. Root: xoá `helper = helper-selector` khỏi `etc/gitconfig` của PortableGit — ảnh hưởng **mọi** repo, và có thể bị ghi lại khi nâng cấp WorkBuddy.
4. Nếu muốn giữ GCM: trong dialog chọn `manager` + tick "Always use this from now on" — nhưng GCM vẫn có thể đòi xác thực tương tác, không hợp với phiên agent.

**Về sandbox** (câu hỏi gốc): cơ chế chính thức là tham số `dangerouslyDisableSandbox` của công cụ Bash — nó **hỏi người dùng xác nhận** rồi mới chạy ngoài sandbox; không phải đường vòng. Cấu hình bền nằm ở `~/.workbuddy-ai/settings.json` → `sandbox.extraAllowWrite` (thêm đường dẫn được ghi) và `sandbox.orderedRules.file` (mỗi path: read/write/delete = allow/ask/deny). Profile sandbox có `default_action: deny_write` + `auto_grant: true`. Nhưng trường hợp này **không cần** — push không bị sandbox chặn.

## Increment 2b-fix — engine VieNeu không chạy trên máy thật (1.3.419, commit `6878448`)

Người dùng báo lỗi **"Graph runtime không trả về tensor mong đợi"** khi bấm Phát thử. Truy ra **3 nguyên nhân, 2 là lỗi thật của lượt 1.3.417**:

### Lỗi 1 — `VieNeuNPZReader` tin vào size của ZIP local header (NGUYÊN NHÂN GỐC)
`np.savez` ghi **`0xFFFFFFFF`** (sentinel **ZIP64**) vào trường `compressed`/`uncompressed size` của ZIP local header, và để kích thước thật ở **extra field / central directory**. Bộ đọc đầu tiên đọc thẳng trường đó ⇒ `entryEnd = 4.294.967.357` trên file 53.448 byte ⇒ ném `badNPZ("vượt biên file")`.
**Cách sửa**: **không dùng kích thước của ZIP** — sau header local, kiểm magic `\x93NUMPY`, đọc header NPY lấy `shape` + `descr`, tự tính `số phần tử × kích thước phần tử`. Đã mô phỏng lại bằng Python trên `constants.npz` thật: 5 entry, size khớp **chính xác** `zipfile` (896 / 51.328 / 224 / 224 / 132). Cách này còn làm con trỏ nhảy đúng qua vùng dữ liệu ⇒ không bao giờ khớp nhầm `PK\x03\x04` tình cờ nằm trong dữ liệu float.

### Lỗi 2 — `prepareLocked()` không nguyên tử (làm lỗi 1 hiện ra SAI CHỖ)
Bản đầu gán `runtime` **trước** khi nạp `config`/`catalog`/`phonemizer`. Khi config ném lỗi ⇒ engine kẹt nửa vời: `isPrepared` trả `true`, mọi lượt sau **nhảy qua bước nạp**, rồi guard tầng dưới báo "Graph runtime…" ⇒ người dùng đi tìm lỗi ở tầng ONNX trong khi nguyên nhân nằm ở bộ đọc NPZ.
**Cách sửa**: dựng hết vào biến cục bộ rồi gán một lần; nhánh null của CFG tách thành `static makeNullBranch(runtime:config:)`. Thông báo đổi `badOutput("runtime")` → `notPrepared`.

### Lỗi 3 — tên output 4 graph là tên TÔI ĐOÁN
Bản tham chiếu Python lấy output theo **chỉ số** (`run(None, {...})[0]`) nên không xác nhận được tên, mà `OrtApi::Run` **bắt buộc** truyền tên ⇒ `"ctx"`/`"out"` là đoán, sai là một lỗi runtime nữa chờ nổ.
**Cách sửa**: bridge C hỏi thẳng session bằng `SessionGetOutputName` ngay sau `CreateSession`, lưu vào `context->outputNames[4]`; tên do allocator mặc định của ORT cấp phát nên trả lại bằng `allocator->Free` trong `VieNeuORTDestroy`. Tên **input** giữ nguyên (bản tham chiếu truyền theo tên ⇒ đã xác nhận).
Chữ ký đã kiểm: `SessionGetOutputCount(const OrtSession*, size_t*)`, `SessionGetOutputName(const OrtSession*, size_t, OrtAllocator*, char**)`, `GetAllocatorWithDefaultOptions(OrtAllocator**)`, `OrtAllocator.Free(struct OrtAllocator*, void*)`.
